# Rework Plan — `subcontratistas`

Once a month, ~80–150 subcontratistas send one `.xlsx` each listing their workers on the Lima-metro project; the operator zips them, uploads the zip, and this app consolidates ~5,000 workers into 18 canonical columns, injects them into `src/template.xlsx`, and produces the monthly *Reporte Social - RRHH*. The rework exists because the delivered report is measurably wrong in five independent ways at once, and every one of those ways is silent — the output always looks complete. This folder holds five documents: what the app does today, what is broken and how badly, what "correct" would look like, which npm packages are worth adding, and the order to do the work in. Everything is verified against the repo and the raw OOXML of the workbooks it reads and writes, as of 31 July 2026.

---

## The short version

- **The report currently in use is wrong, and nothing in the pipeline says so.** Four independent defects, all measured, all silent: **3,757 ghost rows** of empty strings sit inside `Tabla2` in `MAYO_2026` and poison every whole-column `COUNTIF`; **~200 of 5,065 rows** carry text dates that produce `#VALUE!` in `Edad`/`Rango Edades` (36 workers in that bucket on the front page of `FEBRERO_2026`) and drop silently out of the Altas/Bajas counts; **an entire subcontratista vanishes** if its sheet is not named exactly `Cuadro`, logged only to a terminal `console.clear()` has already wiped; and every period classification anchors on `TODAY()-30`, so **the numbers change every time the file is reopened**. See `02-shortcomings.md`.

- **The delivered file is a template with new bytes in A:R and stale everything else.** The pivot cache in every generated report still reads `refreshedBy="Alvaro" refreshedDate="45566.353735300923"` — 1 October 2024. **Five of the fourteen archived reports** (`DICIEMBRE_2024`, `FEBRERO_2025`, `NOVIEMBRE_2025`, `ABRIL_2026`, `MAYO_2026`) still display September-2024 numbers verbatim, because nobody ever opened them in Excel. The report is only correct if a human opens it and hits Refresh, and nothing in the process says so.

- **One subcontratista's workbook is shifted by a column, and 643 real workers count as one person.** In the last run, **643 rows — 12.7%** — have `RUC`/`EMPRESA`/`CONTRATISTA PRNCIPAL`/`Nro. DNI / CE` all absent and the RUC number `20101155588` sitting in `APELLIDOS Y NOMBRES`. Because identity keys on the name, `COUNTIF` returns 643 for each, so all 643 together contribute a headcount of exactly **1** — and `Tipo de Empresa` reads blank = blank as TRUE, tagging every one of them `Principal`. This is the case for anchoring on `RUC`: a shifted sheet can resolve 17 of 18 headers perfectly while every *value* is off by one, so header-matching alone will not catch it. See `02-shortcomings.md` BUG-04.

- **The operator has been downloading the wrong month, wearing the right name.** `src/app.js:124` sorts with `(a, b) => a.ctime + b.ctime` — adding two `Date`s is not a comparator; it yields `NaN` and `sort` is a no-op, so `sortedFiles[0]` is alphabetically `Reporte_Subcontratistas_ABRIL_2026.xlsx`. `public/js/index.js:89` then renames the download to the month the operator expected. This is the cheapest fix in the whole register.

- **Two of your four premises are correct; one is half correct and the wrong half is the dangerous one.** Column *reordering* genuinely works and should be kept. Column *recognition* is exact-string and silently blanks a column. Details in the next section.

- **The packages are not where the value is.** Of twelve dependency questions researched, **two are unambiguous adopts** (`dayjs` for strict day-first text dates, `zod` for per-row validation with full issue accumulation), one is "you already have it" (SheetJS's `range` option and `XLSX.SSF`), and **six answer "no package"**. Six existing dependencies come out. **Net dependency count goes down.** `04-proposed-packages.md`.

- **Keep `xlsx-populate` and keep the template.** The hardest problem in this domain — preserving 13 pivot tables over one shared cache — is already solved by accident: xlsx-populate never parses the parts it does not model, and every pivot part is **SHA-1 identical** between `template.xlsx` and the generated report. ExcelJS would silently delete all six pivot sheets. Do not re-open this.

- **The highest-value fixes need no dependency at all:** anchoring on the normalized `RUC` header, not swallowing the missing-`Cuadro` error, deleting ghost rows instead of blanking them, fixing the download comparator, and taking the report period from the operator instead of the wall clock. The dependencies make the result *trustworthy*; those five make it *correct*.

- **Nothing is retained, by design — so correctness is proved two other ways.** The app deletes its own inputs (`src/app.js:85`, `src/excelConsolidation.js:270`) and you have decided that is fine: no archiving, no logs, no historical material, and no past month reproducible after the fact. Verification rests instead on **(1)** a hand-written, kilobyte-scale, committed fixture corpus — one workbook per known pathology — plus unit tests on the pure functions and structural assertions on the generated workbook, all fully offline and in CI; and **(2)** the **parallel-run cutover**, promoted from a nice-to-have to the primary end-to-end check: for two monthly cycles the operator's single upload is processed by *both* pipelines inside the same job and the two outputs are diffed on the spot, which needs nothing stored. The honest cost, stated once: there is now no way to prove the reworked pipeline reproduces a specific past month's published numbers. That is an **accepted risk**, not an open problem. **There is no blocking prerequisite — the plan starts immediately.** `05-implementation-plan.md` §4.

## Answers to the four questions you raised

**1. Anchor extraction on the first `RUC` header instead of assuming A1 — necessary, and it needs no new package.**
Confirmed: `src/excelConsolidation.js:131-133` calls `sheet_to_json` with default options, which means "header is row 1, table starts at A1". The fix uses APIs already installed — scan `XLSX.utils.decode_range(ws['!ref'])` for the first cell normalizing to `RUC`, then pass `{ range, defval: null, raw: true }`. **One design caveat changes how you write it:** the anchor must define the header **row only**, not the left edge. Your own premise is that column order varies, so a subcontratista who puts `EMPRESA` to the left of `RUC` would lose that column silently — a fresh instance of the exact failure class below, and invisible to the ≥8-of-18 header check because 17 of 18 still resolve. Resolve the span by scanning the header row outward in both directions. `03-expected-output.md` §1.2.

**2. "Column order is already handled" — half true, and the wrong half is the dangerous one.**
`orderHeadersAndData()` (`src/excelConsolidation.js:300-312`) genuinely rebuilds every row in canonical `dataColumns` order, so a workbook that rearranges its columns *is* handled correctly. **Keep that code.** But reordering is the second step; recognition is the first, and recognition is exact, case-, accent- and whitespace-sensitive string equality (`dataColumns.indexOf(key)` at `:66`). `"RUC "`, `"Ruc"`, `"DISTRITO SEGUN DNI"` and — note the asymmetry — the *correctly spelled* `"CONTRATISTA PRINCIPAL"` are all deleted by the cleanup loop before the reorder ever sees them. The column then comes out **present and empty**, which is worse than missing, because nothing distinguishes it from a subcontratista who genuinely left the field blank. A blank `DISTRITO SEGÚN DNI` means that entire company resolves to `Zona de Influencia = "No"` and disappears from the zone report while still counting toward headcount. The fix is one normalizer (trim → collapse whitespace → NFD accent-fold → uppercase) plus an explicit, greppable alias table for genuine spelling differences. `02-shortcomings.md` BUG-03, `03-expected-output.md` §1.3.

**3. Dates arrive in inconsistent formats — confirmed, quantified, and worse than it looks.**
103 text values in `FECHA NACIMIENTO`, 100 in `FECHA INICIO DE LABORES EN OBRA`, out of 5,065 rows, plus malformed years that no strict parser will take (`09/10/205`, `05/09/20258`, `10-11-202-6`). The damage splits into two very different failure modes. The **visible** one is `#VALUE!` in `Edad`/`Rango Edades` — neither is wrapped in `IFERROR`, and 36 workers sit in that error bucket on the client-facing page of `FEBRERO_2026`. The **invisible** one is `Altas`/`Bajas2`, where the `IFERROR(…,"No aplica")` wrapper quietly reclassifies an unparseable date as "did not join / did not leave" — so `Total Ingresos` is systematically low and departed workers stay on the active headcount forever. Day-first is correct and is proved by the template's own number formats (`dd/mm/yyyy;@`, `dd\.mm\.yyyy;@`, `d/mm/yyyy`), not by a locale guess. `03-expected-output.md` §3.

**4. Which packages should replace the hand-rolled code — fewer than you would expect.**
**Adopt two:** `dayjs` + `customParseFormat` (strict mode is the only thing that rejects `09/10/205` and `31/02/2026`; `date-fns` silently yields year 0205 and year 0026) and `zod` (`safeParse` returns *every* failing field with a path — that is the `Errores` sheet the operator has never had). **Promote one transitive to direct:** `jszip@^3.10.1`, already resident via xlsx-populate and load-bearing for the OOXML patch. **Upgrade one:** `adm-zip` → `^0.6.0`, clearing GHSA-xcpc-8h2w-3j85 (HIGH, 4 GB allocation) that `npm audit` reports today. **Change one registry:** `"xlsx": "npm:@e965/xlsx@^0.20.3"` — your call, supply-chain trade-off in `04-proposed-packages.md`. **Remove six:** `googleapis`, `@google-cloud/local-auth`, `exceljs`, `lodash`, `axios` (server-side), `ejs`. **Six questions answer "no package":** header normalization, `Tabla2` resizing, RUC/DNI check digits, testing (`node:test`), concurrency, and the reader itself. `npm audit` reports 23 vulnerabilities today (1 critical, 12 high); the removals plus two upgrades clear nearly all of them.

**`01-current-state.md`** is deliberately descriptive: the runtime flow, the 18-column contract, the anatomy of `template.xlsx` (9 sheets, 13 pivots over one cache, a 43.9 MB `Cuadro` worksheet part), and the deployment. Two sections carry the weight — **§8**, the measured type distribution across the 5,065 rows of the last real run, which is the empirical case for the whole rework; and **§10**, the list of design decisions that are already right and must be preserved deliberately rather than lost by accident: the canonical reordering, the hand-accreted normalization vocabulary, the template-plus-pivot architecture, the two-stage pipeline with a materialised checkpoint, and the zero-friction UX.

**`02-shortcomings.md`** is the defect register — **55 numbered defects**, ranked by what each does to the delivered numbers rather than by how ugly the code is. Thirteen carry a CRITICAL label — one of them only in combination — under a single strict definition: *silently produces a wrong report the operator will trust*. It closes with an explicit assessment of where your assumptions were right and wrong. The most useful property is that every entry carries a "how to prove it" snippet, so nothing has to be taken on faith.

**`03-expected-output.md`** is the acceptance contract: the input tolerances the extractor must have (`__MACOSX/`, lock files, two workbooks in one folder), the anchoring rule step by step, the canonical 18-field record with per-column coercion and validation, the full date specification with worked examples, the per-column rules for the four coded domains, which of the 17 computed columns stay Excel formulas and which become JS literals, and the run report as a new deliverable. It ends with **31 numbered acceptance criteria** and the parallel-run comparison procedure — including the list of divergences that are *expected*, which has to be written and frozen before the first diff is read, so that an *unexpected* divergence is the signal rather than a judgement call made after the fact.

**`04-proposed-packages.md`** is a decision record organised by problem, not by package, because most of the interesting answers are "no". It states the bar a dependency has to clear, then works through twelve questions — reading, writing, table resizing, headless recalculation, dates, validation, header matching, identifiers, zip safety, logging, testing, concurrency. It also contains the strongest evidence in the whole set: the SHA-1 proof that xlsx-populate preserves every pivot part byte-identically, and *why* (it never parses them). It closes with a proposed `package.json`, a removal list, and the `xlsx@0.18.5` supply-chain question laid out as three options.

**`05-implementation-plan.md`** is the build order: **seven phases**, each independently shippable, constrained by the rule that the monthly report must stay runnable throughout. New code lands under `src/pipeline/` alongside the old path, which stays live until two parallel months diff cleanly. It includes the target module layout, the two-part verification strategy (fixtures plus the parallel run) and the accepted risk that no past month can be reproduced, an **11-row risk register**, **9 open questions only you can answer**, and a traceability table mapping all 55 defects and all 31 acceptance criteria to a phase.

| Phase | Goal | Outcome | Effort |
|---|---|---|---|
| **0 — Test harness and fixture corpus** | A deterministic regression gate, buildable today from what is already in the repo — and it changes no production code | `node:test` wired; **~21 hand-written pathology fixtures** (17 workbooks + 4 containers), each with its expected output beside it; pure-function case tables as committed JSON; structural assertion helper (SHA-1 against the *template*); `tools/diff-reports.js`, the parallel-run diff script; `npm test` in CI | 4–5 d |
| **1 — Extraction** | Read every workbook correctly; make an unreadable one impossible to miss | Sheet found by normalized name; `RUC` anchoring with the span resolved outward; header normalizer + alias table; numeric-name rejection; six input tolerances; provenance; run report v1 | 3–4 d |

| **3 — Output integrity** | The workbook that comes out is structurally correct | Ghost rows deleted; placement by column *name*; `Tabla2` resized; `refreshOnLoad` + `fullCalcOnLoad`; twelve surviving formula columns; metrics side-car JSON; real dedupe | 4–5 d |
| **4 — Determinism** | February's report shows the same numbers in March and next year | Explicit period stored in the workbook; five clock-dependent columns become JS literals (and lose their `<calculatedColumnFormula>`); three broken validation formulas fixed; pivot page filters re-pointed; template cleaned | 3–5 d |
| **5 — Server** | The web path stops being the fragile part | Correct download; `path.join`; safe extraction with caps; work moved off the request onto SSE; errors propagate; a fresh per-run temp directory deleted in an awaited `finally`; parallel-run shadow mode | 3–4 d |
| **6 — Cleanup** | Leave a repo you can come back to in a year | Old modules deleted; six dependencies dropped; binaries out of git; `.gitignore` fixed; CI restarts by name; frontend tidy | 1–2 d |

**Total: 21–29 days of focused work**, plus **two** parallel-run months before cutover, which run alongside normal operation rather than adding to the build. At two days a week that is roughly a three-month calendar. Phases 0 and 5 now carry the whole verification strategy between them, which is where the four extra days went — three on Phase 0 and one on Phase 5: hand-authoring 21 fixtures with an expected-output file each is a real week of work, and the shadow-run mode is new.

**Order of attack.** Phase 0 is not optional and not skippable — nothing after it is verifiable without it — and it **can start today**, entirely from material already in the repo, with no data to capture first and no production code touched. After that the order above is also the order of value: Phases 1 and 2 fix what enters the workbook, Phases 3 and 4 fix what leaves it, Phase 5 fixes what the operator receives. If the work stops after Phase 2, the app still runs the old writer but with correct extraction and correct dates — that is a real improvement, not a half-finished migration. **Cut over only on a clean diff after two parallel months, at the start of a month, never in the week the report is due, and keep the old path runnable for one more cycle.**

## Decisions needed from you before work starts

**1. Keep the template, rebuild it, or drop it?**
The plan recommends **Option D — keep the template, keep the twelve lookup/count formulas, compute the five time-dependent columns in JS as literals**. The reasoning: the six pivot sheets *are* the deliverable, no JS library writes pivot tables, and xlsx-populate already preserves all 13 pivot parts byte-identically. Rebuilding the template (Option B) is the largest single chunk of work in the plan with nothing to verify it against; dropping it (Option C) destroys what the client reads. The cost of Option D is two sources of derivation — JS for five columns, Excel for twelve — which must be documented. **Confirm this before Phase 3 starts**, and it is worth one conversation with whoever actually reads the report: if they would accept a flat workbook plus a JS-generated summary, the whole rework gets simpler and fully testable. `05-implementation-plan.md` §5.

**2. Is the DNI or the name the correct identity key?**
The template counts people with `COUNTIF(Tabla2[APELLIDOS Y NOMBRES],…)`, so `"HUARCAYA COCCHE JESUS "` and `"HUARCAYA COCCHE JESUS"` are two people while two genuine homonyms are one. Switching the dedupe key to the DNI would change the headline headcount — and 723 of 5,065 rows have no DNI at all. **This is the one change in the plan that moves numbers the client has already seen**, so it needs explicit sign-off before it ships — and it is due **before the first parallel month**, not during it, because a key change mid-comparison makes the diff unreadable. `05-implementation-plan.md` §8 Q3.

The remaining seven decisions — two-digit years, whether an unparseable date blocks the run, future-dated cese, what to do with the 23 RUCs that fail the mod-11 check digit, prompted vs inferred period, `discrepancias.js`, `@e965/xlsx` vs the CDN tarball — are stated with a recommendation each in `05-implementation-plan.md` §8. None of them blocks the start; each is due at the top of its phase.

## Recommended first three actions

All three can start today; none of them waits on anything.

1. **Fix the download route.** Replace `filesWithStats.sort((a, b) => a.ctime + b.ctime)` at `src/app.js:124` with "serve the exact path this run produced", and delete the duplicated `getMonthAndYear()` at `public/js/index.js:103-111` so the server owns the filename. Twenty minutes, and it stops the operator shipping `ABRIL_2026` to the client under this month's name. While you are in the file, add `path.join` at `:66` and make `src/excelReporting.js:61-63` rethrow so a failed run stops answering `200 OK`.

2. **Build the Phase 0 test harness.** `"test": "node --test src/test/"` in `package.json`; the hand-written fixture corpus in `src/fixtures/` — kilobyte-scale, five to twenty synthetic rows each, one pathology per file, each shipping its expected output as JSON beside it, authored using `src/ReporteConsolidado.xlsx` and `src/template.xlsx` as reference for *shape only*; the pure-function case tables as committed JSON in `src/test/cases/` (dates, headers, coded domains, RUC/DNI check digits — where a silent wrong answer is most likely); and the structural assertion helper that unzips the output and checks `Tabla2`'s ref against the row count, zero empty-string rows inside the table, zero `#VALUE!`/`NaN`, every date cell numeric, the 13 pivot parts' SHA-1s **against the template**, and no dangling relationships. Add `npm test` to `.github/workflows/subcontratistas.yml`. This phase touches no production code, so it cannot break the monthly run — and every later phase is verified through it.

3. **Build `tools/diff-reports.js` and write the expected-divergence list.** The diff script is what the parallel-run cutover — the plan's only end-to-end evidence — is built on, so build it now while the requirements are fresh, and self-test it: a file against a copy of itself must report zero differences. Then freeze the list of divergences the new pipeline is *expected* to produce (`05-implementation-plan.md` §4.5: the ghost rows gone, the text dates now serials, the `#VALUE!` bucket empty, the 643-row block resolved into real workers, `Detalle Cesados` at 79 rows) **before** the first diff is read. A list assembled afterwards will explain whatever it is shown; a frozen one turns every unexplained difference into a hard block on cutover.
